DAC Agent Architecture

A sidecar that keeps each customer's data separate inside shared AI agents. The current focus is shared agent memory: many customers' memories in one vector store, where one bad filter exposes everyone.

How the pieces fit

The agent keeps working as it does today. All of its traffic goes through the DAC sidecar, which sits in the same pod and enforces the customer boundary on the way out and on the way back.

Tenant guard (new core) DAC sidecar Agent pod boundary
TRUST

The customer always comes from the logged-in session, never from the model. The model can write any filter it likes; the sidecar still combines it with tenant = the session's customer before anything reaches the store.

What the tenant guard enforces

The guard speaks Qdrant's REST API. Frameworks need one change: point their Qdrant client at the sidecar. Each framework stores the customer under a different field (metadata.tenant_id, tenant_id, user_id), set per sidecar.

OperationWhat the guard does
ReadsSearch, query, scroll, count and facet all get the customer filter ANDed in, including every sub-query.
WritesEvery record is stamped with the caller's customer. Overwriting another customer's record is refused.
Changes by IDDeletes and updates by record ID only match the caller's own records. The customer tag can't be changed or removed.
ResponsesChecked again on the way back. Records from other customers are removed.
Everything elseRefused by default: dropping collections, snapshots, queries that reuse other records, bulk rewrites.

Known gaps

  • The customer comes from a plain header. The next step is a signed session token from the control plane, which also connects the two halves of the system.
  • Only Qdrant's REST API is covered. Not gRPC, pgvector, Pinecone or Chroma, and nothing stored outside the vector store.
  • The overwrite check has a small race window between checking a record's owner and writing it.
  • Docker packaging needs fixing. The sidecar's Dockerfile has broken paths, so the compose build fails.
